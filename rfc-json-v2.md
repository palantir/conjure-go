# RFC: conjure-go: Generated literal JSON bindings

This proposal concerns the Conjure type and service bindings generated by `conjure-go`.
By generating method implementations that unmarshal and marshal JSON using type-specific
implementations, we avoid the performance overhead of reflection and interface boxing.

While the libraries, framework, and construct proposed may be useful outside the context of conjure,
especially for code generated from other API definitions, those use cases do not have significant
influence in the design of this feature.

🚀🚀🚀 Benchmarks show CPU and Memory cost **8x** lower 📉📉📉

## Background

### Current State of Conjure JSON in Go

The approach to JSON marshaling and unmarshaling is largely unchanged since conjure-go's intial implementation in 2019.
The `encoding/json` package's `Marshal` and `Unmarshal` functions use reflection to identify the type of the target object.
If the the implements the interface methods `MarshalJSON()` or `UnmarshalJSON()`, those methods are used to override the
default reflection-based behavior. As a special case, types that implement `MarshalText()` and `UnmarshalText()` use those if
`MarshalJSON()` or `UnmarshalJSON()` do not exist.

Conjure specifies a number of behaviors that differ from the default encoding and decoding behavior provided by `encoding/json`.
Some of these have existing mitigations described below, but many do not.

- Allocation-heavy and slow (Encoding and Decoding)
- No way to enforce required struct fields (Encoding and Decoding)
- No way to err in case of unknown struct fields (Decoding)
- Difficult to marshal object and map fields in deterministic order (Encoding)
- Difficult to omit empty optional fields in all cases (Encoding)
- JSON 'null' bypasses custom UnmarshalJSON method (Decoding)
- Null collections require custom UnmarshalJSON methods to initialize nil go fields (Decoding)
- Nil collections require custom MarshalJSON methods to render `{}` and `[]` (Encoding)
- Floats use `Inf` and `-Inf` instead of `Infinity` and `-Infinity` (Encoding and Decoding)
- Unions require complex internal serializer and deserializer structs to correctly handle polymorphism (Encoding and Decoding)

We've lived with this for now. Did I mention it's slow?

### Introducing `encoding/json/v2`

In 2024 [github.com/go-json-experiment/json](https://github.com/go-json-experiment/json) surfaced as a proposal for revising
the standard library's JSON package. The [golang proposal](https://github.com/golang/go/issues/71497) has traction and
testing behind a `GOEXPERIMENT=jsonv2` feature flag started in go1.25.
Those READMEs and issues are important for understanding this RFC and the shortcomings of the existing package.

The new [jsontext](https://pkg.go.dev/encoding/json/jsontext) API provides strong JSON syntax and grammar safety with minimal overhead.
The [Encoder](https://pkg.go.dev/encoding/json/jsontext#Encoder) and [Decoder](https://pkg.go.dev/encoding/json/jsontext#Decoder) types
facilitate iterating through JSON [Token](https://pkg.go.dev/encoding/json/jsontext#Token) by Token.
Types implement the [json.MarshalerTo](https://pkg.go.dev/encoding/json/v2#MarshalerTo) and [json.UnmarshalerFrom](https://pkg.go.dev/encoding/json/v2#UnmarshalerFrom) 
interfaces to customize their JSON representation:
```go
package json

type MarshalerTo interface {
	MarshalJSONTo(*jsontext.Encoder) error
}

type UnmarshalerFrom interface {
	UnmarshalJSONFrom(*jsontext.Decoder) error
}
```

Until the V2 package is generally available (go1.26?), our generated code will depend on the `github.com/go-json-experiment/json` module.
When the standard library package can be imported by default, we will switch. We are looking forward to a resolution on [custom options](https://github.com/golang/go/issues/71664)
to more finely tune conjure JSON behavior (e.g. option to allow missing required fields).


## Proposal

**BLUF: Generate implementations of `MarshalerTo` and `UnmarshalerFrom` that are
faster and more correct than today's reflection-based behavior.** 

Conjure knows exactly how a particular type defined in a ConjureDefinition should be encoded and decoded.
So far, we have tried to trick the existing reflection-based behavior into working correctly.
Instead, we should lean into custom methods that implement library interfaces to more exactly control how types are encoded and decoded.
As a bonus, this approach improves performance significantly over the reflection.

**Principles and Goals**

- Make it fast. Reduce heap allocations, interface boxing, reflection, type conversion, variable escape, etc.
  Prove it with go benchmarks and `go build` debug logging.
- Fix incompatibilities with the Conjure Wire Specification and the Conjure Verification Server.
  Some behavior changes ("breaks") are acceptable if they improve spec compliance. For example, servers should reject unknown struct fields.
- Ugly generated and library code is acceptable in hot code paths, but keep it out of user-facing APIs.
  Generated types should implement well-known interfaces that are nicely compatible with idiomatic tools.
  - Users should not need to understand or interact with our complexity but our code should not be incomprehensible and should read as very formulaic.
  - Our types should play nicely with other libraries and APIs that expect hand-crafted types.
- Knock out some long-standing feature requests while we are at it:
  - Error when missing required struct fields
  - Servers reject unknown struct fields
  - Deterministic struct field and map key ordering
  - Simplify conjure unions and make their behavior more explicit
  - Better error messages
